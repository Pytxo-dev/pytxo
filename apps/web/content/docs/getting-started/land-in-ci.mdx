---
title: GitHub Action
description: Check each agent pull request together with the other open ones, with one line of GitHub Actions.
---

Add `.github/workflows/pytxo.yml`:

```yaml
name: Pytxo
on: pull_request
permissions:
  contents: read
  pull-requests: write
  actions: read
concurrency:
  group: pytxo-${{ github.event.pull_request.number }}
  cancel-in-progress: true
jobs:
  check:
    runs-on: ubuntu-latest
    steps:
      - uses: Pytxo-dev/pytxo/actions/land@v2
```

No inputs, no labels, no other steps. `concurrency` stops an older run when the pull request gets a new push, so an old verdict never replaces a newer one. A stopped run posts nothing. `actions: read` lets it see which of Copilot's runs someone let start, so Copilot's pull requests can join the check.

## What it does

On each `pull_request` event:

1. **Is this an agent pull request?** It is when its branch matches `claude/*`, `codex/*`, `copilot/*`, `cursor/*`, `devin/*`, `jules/*` or `agent/*`, or when an agent account opened it (Copilot, Claude, Cursor, Devin or Jules). Anything else ends the job with a note in the job summary.
2. **Which pull requests go together?** This one plus the other open agent pull requests from this repository into the same base branch, oldest first, at most 10. Drafts count. A pull request opened by Copilot or `github-actions[bot]`, whose runs GitHub holds for approval, joins at the newest of its commits whose run someone let start, and the comment names that commit; until then it is left out. If this is the only one, there is nothing to combine.
3. **The check.** It fetches each of those pull requests at the commit this run saw and runs `npx pytxo check` on them, which merges them in a throwaway worktree and runs the test command it finds in the base branch.
4. **The verdict.** It keeps one comment on this pull request, updated by each run that checks it, and writes the verdict to the job summary. A run with nothing to combine creates no comment, but updates one an earlier run left.

On `pull_request_target` it refuses to run. On any other event it does nothing and the job passes.

## When the job fails

The job fails when this pull request conflicts, fails the tests alone, or is in a combination that fails while each pull request passes alone. In that last case every pull request in the combination fails, because Pytxo cannot tell which one is at fault. When nothing in the result points at any of them, such as a combined run that timed out, every pull request in the run fails too. You can make it a required check.

When only other pull requests are to blame, such as a draft that fails on its own or two other pull requests that conflict with each other, the comment names them and the job passes. A flaky result passes with a warning.

A stale result, where the base branch moved during the check, also fails the job; run it again. So does an error, when Pytxo could not run the check.

If no test command is found, the comment says NO TESTS and the job passes; set the `check` input.

## Inputs

All optional.

| Input | Default | Description |
|---|---|---|
| `check` | found in the base branch | Test command, such as `npm ci && npm test` |
| `timeout` | `pytxo check`'s default (900) | Seconds each test run may take |
| `branches` | the agent patterns above | Branch patterns that count as agent pull requests, space-separated |
| `comment` | `"true"` | `"false"` keeps the verdict in the job summary only |
| `token` | `github.token` | Token that lists pull requests and comments. Your tests can reach it too, so give it no other access |
| `license` | none | Pytxo Pro license key for private repositories. Not needed today |
| `version` | the Action's release | Pytxo CLI version from npm |

The `decision` output is `ready`, `blocked`, `stale`, `error` or `skipped`.

## Your tests need their tools

The check runs your own test command, so the runner needs whatever your tests need. GitHub's `ubuntu-latest` has Node.js, and the Action needs Node.js 18 or newer for `npx`. Put your usual setup steps, such as `actions/setup-python` or `astral-sh/setup-uv`, before the Pytxo step.

## Security

- It runs on `pull_request` only. On `pull_request_target` it refuses to run, because that event would run pull-request code with a write token.
- Your tests run in the same job that posts the comment, so code in this repository's agent branches can reach the job's `pull-requests: write` token, as in any CI job that runs that code. Give the workflow no other permissions or secrets.
- By default GitHub runs no workflow on a pull request from Copilot or `github-actions[bot]` until someone with write access approves the run. Such a pull request joins another pull request's run only at a commit whose run someone approved, so its code never runs there without that approval. If your repository turned that approval off, it joins at a commit whose run passed. Without `actions: read` it joins only its own run.
- A run checks each pull request at the commit it saw. A push after someone approved the run does not change what that run tests; the push gets a run of its own.
- A fork's pull request never joins another pull request's run. It is checked in its own run, with GitHub's read-only token and no secrets, so its verdict goes to the job summary. In a private repository, keep GitHub's options that send write tokens or secrets to workflows from fork pull requests turned off.
- The Action's own checkout does not store the token in `.git/config`. If you add your own `actions/checkout` before Pytxo, set `persist-credentials: false`.
- Test output in the comment is redacted for common secret formats and shown as code.
- `permissions` above is all it needs: `contents: read` to fetch the branches, `pull-requests: write` to comment, `actions: read` to see which runs someone let start. Without `pull-requests: write` the verdict goes to the job summary instead.
- It never pushes, merges or changes a branch.

## Private repositories

The Action is free on public and private repositories today. A paid plan for private repositories, Pytxo Pro, is planned; see [Plans](/plans). Once Pro is switched on, the Action on a private repository sends your license key, and nothing else, to Dodo Payments to check it.

## Moving from v1

- `checks` is now `check`.
- `inputs`, `per-input` and `base` are gone. The Action finds the agent pull requests itself and checks them against the pull request's base. Set `branches` only for other branch prefixes: it replaces the default patterns, so don't move `inputs: "agent/*"` into it.
- Remove a `version` pinned to 1.x: the v2 Action runs `pytxo check`, which 1.x does not have.
- Agent pull requests are found by branch prefix or bot author, not by the `agent` label, so drop the label `if:` and the fetch step. Your own `actions/checkout` can go unless a step before Pytxo reads your files, as `actions/setup-node` with `cache: npm` does; if you keep it, set `persist-credentials: false`.
- Commenting needs `pull-requests: write`.
