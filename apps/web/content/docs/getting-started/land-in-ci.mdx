---
title: GitHub Action
description: Check every agent pull request together with the other open agent pull requests, with one line of GitHub Actions.
---

Add `.github/workflows/pytxo.yml`:

```yaml
name: Pytxo
on: pull_request
permissions:
  contents: read
  pull-requests: write
jobs:
  check:
    runs-on: ubuntu-latest
    steps:
      - uses: Pytxo-dev/pytxo/actions/land@v2
```

No inputs, no labels, no other steps.

## What it does

On each `pull_request` event:

1. **Is this an agent pull request?** It is when its branch matches `claude/*`, `codex/*`, `copilot/*`, `cursor/*`, `devin/*`, `jules/*` or `agent/*`, or when an agent account opened it (Copilot, Claude, Cursor, Devin or Jules). Anything else ends the job with a note in the job summary.
2. **Which pull requests go together?** This one plus the other open agent pull requests from this repository into the same base branch, oldest first, at most 10. Drafts count. If this is the only one, there is nothing to combine.
3. **The check.** It fetches those branches and runs `npx pytxo check` on them, which merges them in a throwaway worktree and runs the test command it finds in the base branch.
4. **The verdict.** It posts one comment on the pull request and updates it on every run.

On `pull_request_target` it refuses to run. On any other event it does nothing and the job passes.

## When the job fails

A blocked verdict fails the job only when this pull request is part of the problem: its branch fails the tests on its own, it conflicts with another agent pull request, or it breaks the tests together with one. You can make it a required check.

When the cause is another pull request, such as a draft that fails on its own or two other pull requests that conflict with each other, the comment names it and the job passes. A flaky result passes with a warning.

A stale result, where the base branch moved during the check, also fails the job; run it again. So does an error, when Pytxo could not run the check.

## Inputs

All optional.

| Input | Default | Description |
|---|---|---|
| `check` | found in the base branch | Test command, such as `npm ci && npm test` |
| `timeout` | `pytxo check`'s default (900) | Seconds each test run may take |
| `branches` | the agent patterns above | Branch patterns that count as agent pull requests, space-separated |
| `comment` | `"true"` | `"false"` keeps the verdict in the job summary only |
| `token` | `github.token` | Token that lists pull requests and comments. Your tests can reach it too, so give it no other access |
| `license` | none | Pytxo Pro license key for private repositories. Not needed today |
| `version` | the Action's release | Pytxo CLI version from npm |

The `decision` output is `ready`, `blocked`, `stale`, `error` or `skipped`.

## Your tests need their tools

The check runs your own test command, so the runner needs whatever your tests need. GitHub's `ubuntu-latest` has Node.js, and the Action needs Node.js 18 or newer for `npx`. Put your usual setup steps, such as `actions/setup-python` or `astral-sh/setup-uv`, before the Pytxo step.

## Security

- It runs on `pull_request` only. On `pull_request_target` it refuses to run, because that event would run pull-request code with a write token.
- Your tests run in the same job that posts the comment, so code in this repository's agent branches can reach the job's `pull-requests: write` token, as in any CI job that runs that code. Give the workflow no other permissions or secrets.
- A fork's pull request never joins another pull request's run. It is checked in its own run, with GitHub's read-only token and no secrets, so its verdict goes to the job summary. In a private repository, keep GitHub's options that send write tokens or secrets to workflows from fork pull requests turned off.
- The Action's own checkout does not store the token in `.git/config`. If you add your own `actions/checkout` before Pytxo, set `persist-credentials: false`.
- Test output in the comment is redacted for common secret formats and shown as code.
- `permissions` above is all it needs: `contents: read` to fetch the branches, `pull-requests: write` to comment. Without `pull-requests: write` the verdict goes to the job summary instead.
- It never pushes, merges or changes a branch.
