title: Land branches from any agent tool
description: Use pytxo land to check several agent branches as one combined change, land only what passed, and keep a receipt.
---

> **Pytxo 2.0:** `pytxo land` is now an alias of `pytxo check`, and with no branches it finds the agent branches and the test command on its own and checks against the default branch; see the [Quickstart](/docs/getting-started/quickstart). Branches you name, as on this page, are still checked against the branch you have checked out, and the flags on this page still work.

Agent workspaces such as Orca, Conductor, Superset, the Codex app or Claude Code give each agent its own branch. Each branch can pass its own checks and still break when merged with the others. `pytxo land` checks the combination before any of it reaches your branch.

It needs Pytxo 2.0 or later, Git, and the tools your checks use. It works on Windows, macOS and Linux and does not call any model.

## Check a set of branches

Check out the branch you want to land into, then run this from your repository. Pytxo checks the branches you name against the checked-out branch, or against the default branch if that branch is one of them or no branch is checked out:

```bash
pytxo land agent/cart agent/discount --check "npm ci && npm test" --per-input
```

Pytxo:

1. Resolves each branch and records the files it changed since it split from your branch.
2. For files that more than one branch changed, maps the changes to functions, methods and types. Two branches that changed the same function are listed with `--verbose` even when Git merges them cleanly, and `--strict` blocks them.
3. Merges the branches in the order you gave, in a separate worktree, with Git hooks turned off. A textual conflict blocks the combination.
4. Runs each `--check`, or the test command it finds in the target branch, on the combined result, in a fresh worktree where nothing is installed. When that fails, it runs the same checks on each branch alone (`--per-input` does this first, every time), which shows when every branch passes but the combination fails, and when the check fails everywhere. If the combined run times out, that is the answer: the branches do not run alone after it, it does not run again, and later `--check` commands do not run. If every branch passes a check alone and the combination fails it, the check runs on the combination once more: Pytxo blames the combination only when it fails twice, and calls the check flaky when the second run passes. A flaky check still blocks. The receipt records both runs. When the check fails both times, Pytxo looks for the cause: a definition, such as a function, that one branch renamed or removed and another branch's new code still uses. With three or more branches and a cause, it runs that check on your branch with only those two branches and, if they fail, with only the others (with one other branch, its run alone already was that run): at most two more runs, recorded as `pair:<i>,<j>` and `rest:<k>,...`, so the verdict can clear the branches that pass without them.
5. Prints the verdict in three lines (**READY**, **BLOCKED**, **FLAKY**, **NO TESTS** or **STALE**, then why and what to do next) and writes a receipt.

By default this is **shadow mode**: your branch and working tree do not change. With `--verbose`, the combined commit is kept at `refs/pytxo/land/<receipt id>` so you can inspect it:

```bash
git log --oneline --graph refs/pytxo/land/<receipt id>
```

## Name the agents

Prefix a branch with a label to record which agent wrote it. The verdict names the branch; the label shows in `--verbose` output, in the receipt and in `--json` as each branch's `label`:

```bash
pytxo land codex:agent/cart claude:agent/discount -c "npm test"
```

A pattern expands to matching local branches: `pytxo land 'agent/*' -c "npm test"`.

## Land it

When the result is ready, add `--apply`:

```bash
pytxo land codex:agent/cart claude:agent/discount -c "npm test" --apply
```

- If the target branch is checked out, Pytxo fast-forwards it only if it still points at the commit that was checked. Git refuses if your local changes would be overwritten.
- If it is not checked out (`--into release`), Pytxo moves it with a compare-and-swap: the update succeeds only if the branch still points at the checked commit.

If the branch moved while the gate ran, the decision is **stale** and nothing changes. Run the gate again on the new tip.

`--apply` lands only a tested result. When no test command was found, or package.json has only a lint or build script, it exits with `1` and leaves the target unchanged; name a test command with `--check`.

### When only some branches pass

When the whole combination is blocked, `--apply` lands the largest set of branches that passed every check as that exact set, and leaves the others out, each with why. When a branch fails its checks on its own, the others run together once more first, so with five branches and one failing, the other four land in that run. A branch that has to change gets a fix prompt to paste into its agent. The target moves to the very commit those runs tested, by the same fast-forward or compare-and-swap, and the receipt says what landed and what was left out.

It exits with `2`, so `pytxo land --apply && git push` stops there: read the verdict before you push. After a flaky run, a combined run that timed out or a `--strict` collision, nothing lands. Without `--apply`, a note names the set that would land. When every branch passes alone and Pytxo cannot name why they fail together, one branch lands and the next run takes the others.

The landed history contains one merge commit per input, made by your Git identity (or "Pytxo Land" if none is configured). Commits are not signed, even when your Git config signs commits; sign or squash afterwards if your repository requires it.

## Read the result

| Exit code | Verdict | Meaning |
|---|---|---|
| 0 | READY, LANDED or NO TESTS | No conflict, and every combined check passed or no test command was found |
| 2 | BLOCKED, FLAKY, or LANDED with branches left out | A conflict, a failed or timed-out combined check, a flaky one, or (with `--strict`) the same symbol changed by two inputs. The target moved only if the verdict says LANDED |
| 3 | STALE | The target moved while the gate ran |

The verdict says what happened, why and what to do next. For a failed check, the why line quotes the error line that best explains the failure, such as `TypeError: price is not a function` rather than a count such as `ℹ fail 1`. When the branches pass alone and fail together, and the failing output confirms that one branch renamed or removed a name another branch still uses, the why line says so instead and the next line says which branch to rebase. A cause the output does not confirm shows as a `note` line under the verdict. `--verbose` adds every check run with its error lines, and `pytxo receipts show <id>` has the last 40 lines of each check. `--json` prints the verdict and the full receipt. `--markdown` prints the GitHub Action's pull-request comment.

## Options

| Option | Default | Use |
|---|---|---|
| `--check`, `-c` | found in the target | Command to run on the combined change; repeatable. Without it, Pytxo runs the test command it finds in the target branch; when it finds none, the verdict is NO TESTS: the branches merge, but nothing was tested. |
| `--per-input` | off | Also run the checks on each branch alone |
| `--apply` | off | Land a ready result, or when it is blocked the largest set that passed as that exact set; with no test command found, exit `1` and change nothing |
| `--into <branch>` | the checked-out branch, or the default branch if it is one of the inputs or none is checked out | Target branch; `git config pytxo.into` or `PYTXO_INTO` sets it too |
| `--base <rev>` | target tip | Check against another commit (shadow mode only) |
| `--strict` | off | Block when two inputs changed the same function or type |
| `--timeout <seconds>` | 900 | Per-check timeout |

Checks run in a fresh worktree, so install dependencies inside the check when needed, for example `--check "npm ci && npm test"`.

## In a pull request

The GitHub Action checks an agent pull request together with the other open agent pull requests into the same base branch and keeps one comment with the verdict on it. See [GitHub Action](/docs/getting-started/land-in-ci).

## Limits

- Pytxo checks what your commands check. Passing checks do not prove the code is right.
- Symbol mapping covers Rust, TypeScript, JavaScript, Python, Go, Java, C/C++ and Ruby. Other files are compared by path only.
- Inputs are merged in the order given; a different order can produce a different result when files overlap.
- The gate does not rebase, squash or resolve conflicts for you.

Every decision leaves a [receipt](/docs/concepts/receipts).
