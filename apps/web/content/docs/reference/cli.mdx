Binary: `pytxo`. This page describes **2.0.0**. Run it with `npx pytxo`, or keep it on your PATH with `npm i -g pytxo`.

## Commands

| Command | Description |
|---------|-------------|
| `pytxo` | Check the agent branches together: the same as `pytxo check` |
| `pytxo check [branch]...` | Check these branches, or the detected agent branches, together. `pytxo land` is an alias |
| `pytxo demo` | Check a throwaway repository where two agent branches pass alone and fail together; `--keep` keeps it |
| `pytxo hook` | Run the check from a Claude Code or Codex `Stop` hook ([guide](/docs/getting-started/agent-hooks)); `--block` asks the agent to fix a BLOCKED verdict |
| `pytxo receipts` | List this repository's receipts; `pytxo receipts show <id>` prints one and checks its digest ([receipts](/docs/concepts/receipts)) |
| `pytxo bench` | Pybench: offline benchmarks of the check ([method](/docs/evidence/pybench)) |

## `pytxo check`

| Flag | Description |
|------|-------------|
| `[branch]...` | Branches or patterns to check. Default: the detected agent branches |
| `--into <branch>` | Target branch. Default: the default branch (`origin/HEAD`, else `main`, `master` or `trunk`, else the checked-out branch); when you name branches, the branch you have checked out, or the default branch if that branch is one of them or no branch is checked out |
| `--base <rev>` | Check against another commit instead of the target's tip (not with `--apply`) |
| `-c`, `--check <cmd>` | Test command, repeatable. Default: found in the target branch |
| `--per-input` | Run the checks on each branch alone every time, not only after the combined change fails |
| `--apply` | Land a READY result on the target by fast-forward or compare-and-swap; refused if the target moved |
| `--strict` | Block when two branches changed the same function or type |
| `--timeout <s>` | Per-check timeout in seconds (default 900) |
| `-v`, `--verbose` | Also print every check's output, the receipt and the digests |
| `--json` | The verdict, what was found and the receipt, as JSON |
| `--markdown` | The verdict as a pull-request comment |
| `--repo <path>` | Repository (default: the current directory) |

Exit codes: `0` ready, landed or nothing to check, `2` blocked, `3` stale (the target moved during the check), `1` error.

With no branches given, Pytxo checks branches that match the patterns below and have a commit in the last 14 days. The pattern `worktrees` means every branch checked out in a linked worktree; Pytxo's own temporary worktrees never count. The test command comes from the target branch: `package.json` (npm, pnpm, yarn or bun, installing dependencies first when there are any), Cargo, Go, uv, Poetry, pytest, Deno, Gradle, Maven, .NET, Mix, RSpec, Rake, Composer or a `Makefile` with a `test` target.

| `git config` key | Environment variable | Default |
|------|------|------|
| `pytxo.branches` | `PYTXO_BRANCHES` | `claude/* codex/* copilot/* cursor/* devin/* jules/* agent/* worktrees` |
| `pytxo.check` | `PYTXO_CHECK` | found in the target branch |
| `pytxo.days` | `PYTXO_DAYS` | `14` |
| `pytxo.into` | `PYTXO_INTO` | see `--into` above |

## Pytxo 1.x commands

The released binaries are the check only. In them, `pytxo review`, `pytxo run` and the other commands below say they are not in this build; `pytxo receipts share` and `pytxo bench --submit` are not there either. The commands are frozen and build from source with the default `full` feature (`cargo build -p pytxo-cli`), where `pytxo shell` opens the interactive shell that a bare `pytxo` opened in 1.x. `pytxo hitl` is the **Galaxy approval queue**, not Apply.

| Command | Description |
|---------|-------------|
| `pytxo review <run>` | Show a finished run's prepared change, checks and digest; `--refresh`, `--discard` |
| `pytxo apply <run>` | Write exactly the reviewed files; refused if anything moved |
| `pytxo receipts share <id>` | Publish a receipt's counts and outcomes as a page (account perk); `--include-paths`, `--private` |
| `pytxo bench --submit` | Publish the summary to the [Pybench board](/bench) (account perk); `--private` keeps it off the board |
| `pytxo login` / `logout` / `whoami` | Optional account for perks ([account](/docs/getting-started/account)) |
| `pytxo init` | Create `.pytxo/` dirs and gitignore hint |
| `pytxo doctor` | Verify git, PTY, approvals persistence, billing/cloud when enabled |
| `pytxo run` | Schedule and execute agents in isolated copies |
| `pytxo mission` | Natural-language mission: plan → approve → isolated run → review package |
| `pytxo agents` | List registered agent CLIs and PATH detection |
| `pytxo accounts` | Several sign-ins per agent CLI (Claude Code, Codex) and which one new work uses |
| `pytxo shell` | The interactive shell, or one command with `--eval` |
| `pytxo status` | List runs and agents from SQLite |
| `pytxo logs --agent <id>` | Tail stored stdout/stderr events |
| `pytxo stop` | Stop active run or all tracked processes |
| `pytxo domains` | List registered execution domains |
| `pytxo project` | Multi-root modular project manifest |
| `pytxo fleet` | Cross-repo fleet DAG |
| `pytxo hitl` | Galaxy human-in-the-loop **approval queue** (risky commands; not Apply) |
| `pytxo trust [tier]` | Trust repo folder (`orbit`, `galaxy`, ...) |
| `pytxo providers` | Provider registry + key configured (boolean) |
| `pytxo models` | List, search, or refresh model catalog |

## `pytxo review` and `pytxo apply`

```bash
pytxo review <run-id>                 # files, checks on the combined change, digest
pytxo apply <run-id> --digest <sha>   # apply exactly that package
pytxo apply <run-id>                  # shows the package and asks before applying
pytxo review <run-id> --refresh       # re-prepare a stale review
pytxo review <run-id> --discard       # drop it; nothing is written
```

Apply authorizes the digest you were shown, never "whatever is latest". If the project changed after review, Apply refuses; refresh and review again. Every committed Apply writes a receipt.

## `pytxo mission`

```bash
pytxo mission "Add input validation in src/api.ts"
pytxo mission "…" --yes          # skip interactive plan approve
pytxo mission "…" --json         # print plan JSON; no dispatch
pytxo mission "…" --ade claude   # preferred ADE id
```

`--plan-file` writes plan JSON before the approve step. After a successful Orbit or Galaxy run, review and Apply in Desktop — not with a CLI apply subcommand. See [Review and Apply](/docs/getting-started/review-and-apply).

## `pytxo agents`

Lists ADE CLIs from the registry and whether they are on `PATH`. `--json` for scripts.

## `pytxo accounts`

Keep more than one sign-in for an agent CLI, such as a work and a personal
Claude account. Each account is the CLI's own config folder under
`~/.pytxo/agent-accounts/<cli>/<name>/`, selected for each launch through the
variable the vendor documents (`CLAUDE_CONFIG_DIR`, `CODEX_HOME`). Sign-in
runs the vendor's own command; Pytxo never reads or copies the credentials it
writes. `default` is the CLI's usual sign-in.

```bash
pytxo accounts list            # every account and its sign-in state
pytxo accounts add claude work # creates the folder, opens Claude Code sign-in
pytxo accounts use claude work # new work on Claude Code uses this account
pytxo accounts login codex     # sign the default Codex account in again
pytxo accounts remove claude work
```

A configured agent can pin an account in `pytxo.toml` with `account = "work"`.
Desktop shows the same accounts under **Setup → Agent CLIs**. Cursor Agent,
Antigravity and Gemini CLI keep one sign-in per OS user, so they have no
accounts list.

Every account must be yours. Provider terms forbid sharing an account and
working around usage limits, so Pytxo never switches accounts on its own when
one reports a limit; it tells you which account hit it.

## `pytxo shell`

`pytxo shell` opens the interactive shell; `--eval` runs one command without it:

```bash
pytxo shell --eval "/dry-run"
```

## `pytxo run` flags

| Flag | Default | Description |
|------|---------|-------------|
| `--agents` | `3` | Max parallel agents per wave |
| `--cmd` | `echo pytxo` | Shell command in each isolated copy |
| `--dry-run` | off | Print JSON execution plan |
| `--keep-worktrees` | off | Do not remove isolated copies after run |
| `--execution` | from config | Override `pty`, `subprocess`, or `cloud` |
| `--ade` | unset | Registry ADE id (e.g. `cursor`, `claude`) |

## `pytxo project` subcommands

| Subcommand | Description |
|------------|-------------|
| `init <id>` | Create project manifest under `~/.pytxo/projects/` |
| `list` | List path roots for a project |
| `paths --add <path>` | Add a path root |
| `remove` | Remove a path root (by label or path) |
| `status` | Recent runs for the project primary domain |
| `run` | Coordinated run across project roots |

## `pytxo fleet` subcommands

| Subcommand | Description |
|------------|-------------|
| `init <id>` | Create fleet manifest under `~/.pytxo/fleets/` |
| `dry-run` | Print fleet execution plan JSON |
| `run` | Run fleet DAG with barrier sync |
| `status` | List fleet runs from hypervisor catalog |

`pytxo fleet run --continue-on-error` continues later waves after a node failure.

## `pytxo hitl` subcommands

Galaxy's approval queue for risky host actions. Approving a HITL request is **not** repository Apply.

| Subcommand | Description |
|------------|-------------|
| `list` | Pending approval requests |
| `approve <id>` | Approve a request |
| `deny <id>` | Deny a request |

See [Galaxy approvals](/docs/concepts/galaxy-approvals) and [Review and Apply](/docs/getting-started/review-and-apply).

## `pytxo trust`

```bash
pytxo trust orbit
pytxo trust galaxy --repo /path/to/repo
```

Tiers: `deep_space`, `orbit`, `galaxy`, `supernova`. See [Permission tiers](/docs/reference/permission-tiers).

## Environment variables

| Variable | Purpose |
|----------|---------|
| `PYTXO_REPO` | Default git root (useful for MCP) |
| `PYTXO_PLANNER` | Enable natural-language mission planner (`1`) |
| `PYTXO_ULTRA_SESSION` | Bearer token for Ultra / Link reconcile when `billing.mode = ultra` |
| `PYTXO_CLOUD_SESSION` | Bearer token for cloud execution when enabled |
| `PYTXO_DEEPSPACE_WFP` | Windows DeepSpace WFP opt-in (`1`) |

Provider API keys stay in their usual env vars (`ANTHROPIC_API_KEY`, `OPENAI_API_KEY`, ...). See [Providers & BYOK](/docs/reference/providers-byok).
